# Local monitoring backend

Implemented local delivery: Alembic migration for immutable revisions, monthly snapshots and adjacent comparisons; a fail-closed validating import/activation command; GET `/api/v1/projects`, GET `/api/v1/projects/{project_code}`, GET `/api/v1/projects/{project_code}/history`, and GET `/api/v1/portfolio-summary`. Uses FastAPI/Pydantic, SQLAlchemy and PostgreSQL through psycopg. No frontend, predictions, deployment or authentication implementation is included. History and portfolio reuse the validated stored adjacent comparisons; they never load April-August pair review decisions or recalculate eligibility.

## Local setup (PowerShell, repository root)

Requires Python with the pinned extraction/backend dependencies, Docker Desktop running, matching source PDFs under data/raw/, and regenerated full extraction/history outputs. Source acquisition and regeneration: [monthly history](monthly-project-history.md). The importer requires all five sources, reviewed fixtures, audits and outputs matching [the revision manifest](examples/dataset-manifest.json); it never trains models or creates missing values.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-backend.txt
$localPassword = Read-Host 'Choose a local PostgreSQL password' -AsSecureString
$env:SENTINEL_DB_PASSWORD = [System.Net.NetworkCredential]::new('', $localPassword).Password
$encodedPassword = [uri]::EscapeDataString($env:SENTINEL_DB_PASSWORD)
$env:DATABASE_URL = "postgresql+psycopg://sentinel:$encodedPassword@127.0.0.1:5433/sentinel"
docker compose -f compose.backend.yaml -p sentinel-backend up -d --wait
$env:API_HOST = '127.0.0.1'
$env:API_PORT = '8000'
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m backend.import_dataset
.\.venv\Scripts\python.exe -m backend.serve
```

The database is exposed only at 127.0.0.1:5433; the API launcher only permits loopback addresses and defaults to 127.0.0.1:8000. DATABASE_URL must explicitly use postgresql+psycopg and a loopback host. `.env.example` documents defaults; environment variables are read directly, not automatically loaded from .env. Compose requires SENTINEL_DB_PASSWORD from the local environment; .env.example contains placeholders only. Keep actual passwords and connection URLs in ignored .env files or process environment variables, never source control. An existing PostgreSQL volume retains its original password: use that credential; changing POSTGRES_PASSWORD does not rotate an initialized database password. Database files persist in a named Docker volume. Stop services without deleting data: `docker compose -f compose.backend.yaml -p sentinel-backend stop`; stop the API with Ctrl+C. Never use volume deletion to refresh a revision.

Authentication and authorization are required before any shared deployment. Do not expose this unauthenticated service on LAN or public interfaces. Local Swagger/OpenAPI documentation is at http://127.0.0.1:8000/docs. No arbitrary externally bound launch or shared deployment is provided.

## Import and immutability

The manifest must be canonical JSON with schema_version project-data-v1, exact source/code/dependency/catalog/reference/output hashes and no active canonical mappings. Validation enforces all full audits, empty rejected-row logs, source/CSV/reference hashes and the validated history audit. It reconstructs history rows and every adjacent output from reviewed inputs and checks generated bytes/hashes, catching stale normalization or comparisons even if a CSV has a freshly edited hash. Input bytes used for the revision archive are checked against validated hashes to reject changes during validation. Run from repository root; supported bundle layout is currently exactly the documented April-August catalog and data paths.

Before DB activation, archive all validated manifest, sources, code, catalog, references, audits, issue logs and outputs under ignored `data/revisions/<manifest-hash>/`, preserving separate revisions. Existing bytes are checked and never overwritten. A failed archival write leaves a retryable partial archive; it does not change the active database. A DB failure can leave a complete unactivated archive for diagnosis. No automatic cleanup deletes prior revisions.

Import uses one SQLAlchemy transaction: lock the singleton active pointer, insert the immutable revision/snapshots/comparisons, then update the pointer and commit. Unique snapshot keys are `(version, project_code, report_month)`; comparison foreign keys require both observed snapshots. Any insertion/activation failure rolls back the entire transaction and preserves the previous active revision. Reimporting the same validated revision is idempotent. Earlier versions remain queryable with dataset_version. PostgreSQL triggers reject updates/deletes/truncation to revision data; the pointer alone is mutable. This is application integrity, not protection from a privileged database administrator. Alembic downgrade is destructive and is not a revision refresh operation.

Raw strings and structured provenance/quality are retained in JSON with normalized decimal strings, never float conversion. Snapshot identity fields are separately indexed/filterable; names and identifiers are unmodified. Source missing markers and verified May blanks map to null with distinct reasons; zero remains string "0". Unknown availability remains null. Source/report warnings are returned at envelope level and field-specific missing/date flags inside snapshot quality. Pair-wide trend gates are retained in stored comparisons, not reinterpreted as field usability.

## Requests and errors

```powershell
Invoke-RestMethod 'http://127.0.0.1:8000/api/v1/projects?report_month=2026-08&page=1&page_size=2'
Invoke-RestMethod 'http://127.0.0.1:8000/api/v1/projects?report_month=2026-08&project_code=701530&project_code=400298&sector=Railways'
Invoke-RestMethod 'http://127.0.0.1:8000/api/v1/projects/701530?report_month=2026-07'
```

The [contract](api_contract.md) defines exact repeated filters (OR within a field / AND across fields), literal case-insensitive name search, stable string-code pagination and error envelopes. There is no latest-month fallback. Explicit unavailable report/version and unobserved snapshot return the documented 404 codes; invalid/unknown query parameters return 422; no active validated revision returns 503. Unexpected errors return generic INTERNAL_ERROR without database URLs, source filesystem paths or stack traces.

```powershell
.\.venv\Scripts\python.exe -m alembic check

```

Backend integration tests require real loopback PostgreSQL and create a uniquely named disposable test schema in the configured database. They migrate that schema, import the complete validated dataset and remove only that schema afterward. They verify rollback after partial inserts/duplicate keys, corrupt manifests and failed audits, database row immutability, prior-revision access, archival preservation, repeated filters/intersections, literal search, pagination, null/zero/raw/provenance values and contract errors. Existing April/August/history tests still run. Without BACKEND_TEST_DATABASE_URL, PostgreSQL tests are explicitly skipped, not reported as proven.

## Remaining limitations

This is a local first delivery, with synchronous DB access and no authentication, frontend, load benchmark or automated revision retention. The catalog/manifest validator supports the reviewed five-month layout only; other months/schema/mappings need explicit versioned work. The archive and DB are separate resources: activation is atomic in PostgreSQL, not a cross-filesystem distributed transaction. Artifact archives and DB volumes need a future backup policy. Source values and identity/scope issues remain unresolved; passing import integrity checks does not certify all measurements. Conservative screening is not silently relaxed.

## History and portfolio requests

```powershell
Invoke-RestMethod 'http://127.0.0.1:8000/api/v1/projects/611752/history?page_size=1'
Invoke-RestMethod 'http://127.0.0.1:8000/api/v1/projects/400298/history?from_month=2026-06&to_month=2026-07'
Invoke-RestMethod 'http://127.0.0.1:8000/api/v1/portfolio-summary?report_month=2026-08&comparison_month=2026-07'
```

History defaults to the selected revision's report bounds, returns snapshots in ascending report month and explicitly lists not_observed_months. Comparisons are selected from stored adjacent pairs over the full requested range before pagination, including on an empty page beyond the end. A June gap for 611752 retains April-May and July-August comparisons only; it never creates a May-July trend. A known code with no observations in a supported range returns an empty history; an unknown code returns PROJECT_NOT_FOUND. Unavailable reports/version and invalid range/parameters use contract error envelopes. Explicit dataset_version works for all endpoints.

Portfolio comparison_month must be the preceding calendar month; omitting it returns comparison null. Repeated exact ministry/sector/state/agency filters are OR within a field and AND across fields, applied independently to both reports. Unfiltered indexes distinguish not_in_filtered_scope from not_observed_in_report. For example, 400298 changes agency from (South Central Railway [SCR] - II) in June to (CAO/C/SCoR SCoR mor) in July: filtering either agency creates a scope membership change, not a claim of project entry/completion. Presence details and grouped reasons expose that difference. Before/after scope counts reconcile to shared and one-sided counts; missing-input counts use shared codes as denominator. Missing fields and exclusion reasons may overlap.

Unfiltered July-August: 1,694 shared, 81 before-only, 37 after-only; progress/expenditure decreases 13/54; zero conservative trend-eligible matches because every shared revised-cost baseline changes to August's literal zero. This is a policy outcome, not proof of usability or unusability of any individual measurement. Raw values and field-specific reasons remain accessible in history; no causes or completion statuses are inferred. Report warning provenance is retained from the imported revision. Headline added/commissioned roll-forward alerts from the research audit are not stored in the first-delivery revision metadata and are not reconstructed from runtime files; see monthly-history documentation for those source limitations.

All responses remain local and unauthenticated; no deployment is provided. Current summary computation loads the two months' snapshots and relevant comparisons into memory and has no load benchmark or cache. Summary presence details and history comparison metadata are unpaginated by contract, bounded by the current five-month dataset. Future larger datasets may require a separately reviewed pagination/performance contract. No schema migration or dataset reimport is needed for these read endpoints.
